01 Overview

What Is Pydantic AI?

Pydantic AI is a Python agent framework built by the team behind Pydantic — the validation library used by virtually every Python GenAI SDK (OpenAI, Anthropic, LangChain, the list goes on). Their pitch is simple: bring the ergonomics that made FastAPI the default web framework to the messy world of building LLM agents.

Where most frameworks bolt structure onto raw text, Pydantic AI treats type-safety and validation as the foundation. Your agent's output is a Pydantic model. Your tools' arguments are validated against their type hints. Your dependencies are injected with full type-checker support. When the model returns something that doesn't fit, the framework feeds the validation error back to the model and lets it correct itself.

🧱

Built by the Pydantic team

From the people whose library powers the validation layer of the OpenAI SDK, LangChain, LlamaIndex and more. Pydantic AI is the agent layer on top of that foundation.

🔒

Type-safe by design

Agents are generic over their dependency and output types. Your IDE and mypy/pyright catch mistakes before runtime, not after a 3am pager.

🔌

Model-agnostic

OpenAI, Anthropic, Google, Groq, Mistral, Cohere, Bedrock, DeepSeek, Grok, Ollama, OpenRouter and more — swap providers with a single string.

📊

Observability built in

Native Pydantic Logfire + OpenTelemetry integration. Every model call, tool call and validation retry is traced out of the box.

The one-liner. If LangGraph is "explicit graphs for control freaks" and CrewAI is "agents as a team of coworkers", Pydantic AI is "agents as type-safe functions" — minimal surface area, maximal validation, production-grade plumbing underneath.

02 Agent Anatomy

The Anatomy of an Agent

An Agent is a reusable, declarative container — you define it once (typically at module scope, like a FastAPI APIRouter) and run it many times. It binds together five things:

ComponentConstructor argumentWhat it does
ModelmodelWhich LLM to call, as a 'provider:model' string or a model object. Can be overridden per-run.
InstructionsinstructionsThe system guidance. Static strings, or dynamic functions decorated with @agent.instructions.
Dependenciesdeps_typeA type (often a dataclass) describing what the agent's tools and prompts need at runtime — DB connections, API clients, the current user.

RetriesretriesHow many times the agent may self-correct on a validation or tool error before giving up.

A fully-typed agent at a glance

from dataclasses import dataclass
from pydantic import BaseModel
from pydantic_ai import Agent, RunContext


@dataclass
class SupportDeps:           # injected at run time
    customer_id: int
    db: DatabaseConn


class SupportOutput(BaseModel):  # validated result
    advice: str
    block_card: bool
    risk: int


support_agent = Agent(
    'openai:gpt-5.2',
    deps_type=SupportDeps,
    output_type=SupportOutput,
    instructions='You are a support agent for a bank. Assess risk 0-10.',
)

Generics matter. support_agent has the static type Agent[SupportDeps, SupportOutput]. Pass the wrong deps to .run() and your type-checker complains before the code ever runs. This is the single biggest day-to-day difference from string-in/string-out frameworks.

03 Defining & Running

Running an Agent

There are four ways to execute an agent, all sharing the same configuration. Pick based on your runtime and how much control you need over the loop.

await agent.run()

The async workhorse. Returns an AgentRunResult once the run completes.

agent.run_sync()

A blocking wrapper around run() for scripts, notebooks and sync codebases.

agent.run_stream()

An async context manager that streams the response — text or structured — as it arrives.

agent.iter()

Iterate the underlying graph node-by-node for full control and inspection of every step.

Three run styles, one agent

import asyncio
from pydantic_ai import Agent

agent = Agent('google:gemini-2.5-flash')

# 1 — synchronous
result = agent.run_sync('What is the capital of Italy?')
print(result.output)        #> Rome
print(result.usage())       # RunUsage(input_tokens=..., output_tokens=...)

# 2 — async
async def main():
    result = await agent.run('What is the capital of France?')
    print(result.output)    #> Paris

    # 3 — streaming
    async with agent.run_stream('Name three Italian cities.') as response:
        async for chunk in response.stream_text(delta=True):
            print(chunk, end='')

asyncio.run(main())

The result object

Every completed run returns a result exposing the validated .output, token .usage(), and the full message log for the conversation:

result = agent.run_sync('How many moons does Mars have?')

result.output            # the validated, typed answer
result.usage()           # token + request counts for cost tracking
result.all_messages()    # every ModelRequest / ModelResponse in the run
result.new_messages()    # just the messages from this run (for history)
04 Type-Safe Outputs

Structured, Validated Outputs

This is Pydantic AI's headline feature. Set output_type to anything Pydantic can validate and the framework instructs the model to produce matching data, parses it, and validates it — handing you back a real Python object, not a string you have to json.loads() and pray over.

A Pydantic model as the output type

from pydantic import BaseModel
from pydantic_ai import Agent


class CityLocation(BaseModel):
    city: str
    country: str
    population: int


agent = Agent('openai:gpt-5.2', output_type=CityLocation)

result = agent.run_sync('Where were the 2012 Olympics held?')
print(result.output)
#> city='London' country='United Kingdom' population=8866000
print(result.output.population)   # a real int, fully type-checked

Beyond a single model

  • Unions — output_type=Success | Clarify lets the model choose between outcomes (e.g. "I answered" vs "I need more info"). The framework exposes each as a separate tool to the model.
  • Output functions — pass a function as the output type and the model's structured call is routed through your code, which can run logic and even raise ModelRetry.
  • Output validators — register @agent.output_validator for cross-field or I/O-bound checks that need RunContext (e.g. "does this SQL actually execute?").
  • Native vs tool output — Pydantic AI uses provider-native structured output (JSON schema / grammar) where available, and falls back to tool-calling otherwise — transparently.

An output validator that re-prompts on failure

from pydantic_ai import Agent, ModelRetry, RunContext

agent = Agent('openai:gpt-5.2', output_type=str, deps_type=DatabaseConn)


@agent.output_validator
async def validate_sql(ctx: RunContext[DatabaseConn], query: str) -> str:
    try:
        await ctx.deps.explain(query)        # dry-run the SQL
    except QueryError as e:
        raise ModelRetry(f'Invalid query: {e}. Try again.')  # model self-corrects
    return query
05 Tools & Function Calling

Tools & Function Calling

Tools are how an agent reaches outside the model — querying a database, calling an API, doing maths. In Pydantic AI you write a plain Python function with type hints and a docstring; the framework derives the JSON schema the model sees from your signature, validates the model's arguments against it, and dispatches the call.

Two decorators

@agent.tool

For tools that need run context. The first parameter is ctx: RunContext[Deps], giving the tool typed access to dependencies, usage, retry count and message history.

@agent.tool_plain

For context-free tools — pure functions of their arguments. No RunContext parameter.

A context-aware tool, with docstring-derived schema

from pydantic_ai import Agent, RunContext

agent = Agent('openai:gpt-5.2', deps_type=SupportDeps)


@agent.tool
async def customer_balance(
    ctx: RunContext[SupportDeps], include_pending: bool
) -> float:
    """Return the customer's current account balance.

    Args:
        include_pending: Whether to include pending transactions.
    """
    return await ctx.deps.db.get_balance(
        id=ctx.deps.customer_id, pending=include_pending
    )


@agent.tool_plain
def roll_die() -> int:
    """Roll a six-sided die and return the result."""
    return random.randint(1, 6)

Docstrings become documentation the model reads. Pydantic AI parses Google-, NumPy- and Sphinx-style docstrings to populate parameter descriptions in the JSON schema. Good docstrings → better tool use. The function's type hints become the parameter types, validated by Pydantic before your code runs.

Tool-level retries

A tool can raise ModelRetry to tell the model "that didn't work, here's why — try again" without crashing the run. This turns a tool into a self-correcting conversation:

@agent.tool
async def get_user(ctx: RunContext[Deps], name: str) -> User:
    """Look up a user by their full name."""
    user = await ctx.deps.db.find_user(name)
    if user is None:
        raise ModelRetry(
            f'No user named {name!r}. Ask the customer for their full legal name.'
        )
    return user

Other ways to register tools: pass a list via Agent(..., tools=[...]), use Tool objects for fine-grained control, or attach toolsets — reusable, composable bundles of tools (including remote ones over MCP).

06 Dependency Injection

Dependency Injection

Borrowed straight from FastAPI: rather than reaching for globals, your tools and dynamic instructions declare what they need, and you supply it at run time. The dependencies are typed, so the wrong shape is a type error — and trivially swappable for tests.

Declare deps, inject at run time

from dataclasses import dataclass
import httpx
from pydantic_ai import Agent, RunContext


@dataclass
class Deps:
    http_client: httpx.AsyncClient
    api_key: str


weather_agent = Agent('anthropic:claude-sonnet-4-6', deps_type=Deps)


@weather_agent.instructions      # dynamic, per-run system guidance
def add_units(ctx: RunContext[Deps]) -> str:
    return 'Always report temperatures in Celsius.'


@weather_agent.tool
async def get_forecast(ctx: RunContext[Deps], city: str) -> dict:
    """Fetch the forecast for a city."""
    r = await ctx.deps.http_client.get(
        'https://api.weather.example',
        params={'q': city, 'key': ctx.deps.api_key},
    )
    return r.json()


async def main():
    async with httpx.AsyncClient() as client:
        deps = Deps(http_client=client, api_key='...')
        result = await weather_agent.run('Will it rain in Leeds?', deps=deps)
        print(result.output)

Why this is a big deal for testing. Because deps are injected, you can construct a fake Deps in a unit test and run the agent against a stub database with zero monkeypatching. Combined with TestModel (see §13), you get fully offline, deterministic agent tests.

07 Validation & Self-Correction

The Self-Correction Loop

Pydantic AI's "reflection" is what turns validation from a wall into a feedback channel. When the model produces output or tool arguments that fail Pydantic validation — or when your code raises ModelRetry — the error message is sent back to the model as a new request, and the model tries again, up to the configured retries limit.

Setting the retry budget

# Whole-agent default
agent = Agent('openai:gpt-5.2', output_type=SupportOutput, retries=3)

# Per-tool override
@agent.tool(retries=5)
async def flaky_lookup(ctx: RunContext[Deps], q: str) -> str:
    ...

If retries are exhausted, the agent raises UnexpectedModelBehavior — a clean, catchable signal rather than a silently-wrong answer.

08 Streaming

Streaming — Including Structured Output

Plenty of frameworks stream text tokens. Pydantic AI's trick is streaming structured output: as the JSON arrives, it is progressively parsed and validated, so you can render a partial, type-safe object live — and reject malformed partials before they reach your UI.

Streaming validated, partial structured output

from pydantic import BaseModel
from pydantic_ai import Agent


class UserProfile(BaseModel):
    name: str
    age: int | None = None
    interests: list[str] = []


agent = Agent('openai:gpt-5.2', output_type=UserProfile)


async def main():
    async with agent.run_stream('Build a profile for a hiker named Sam.') as response:
        async for profile in response.stream_output():
            print(profile)   # a validated (possibly partial) UserProfile each step
  • stream_text(delta=True) — token deltas for plain-text agents.
  • stream_output() — progressively-validated structured objects.
  • agent.iter() — drop down to the node level to observe model requests, tool calls and the end node as they happen.

Fallback models

Wrap several models in a FallbackModel and Pydantic AI tries them in order, moving to the next on error — instant resilience against a provider outage or rate limit.

from pydantic_ai import Agent
from pydantic_ai.models.fallback import FallbackModel
from pydantic_ai.models.openai import OpenAIChatModel
from pydantic_ai.models.anthropic import AnthropicModel

fallback = FallbackModel(
    OpenAIChatModel('gpt-5.2'),
    AnthropicModel('claude-sonnet-4-6'),
)
agent = Agent(fallback)   # try OpenAI, fall back to Anthropic on failure
10 Messages & History

Messages & Conversation History

Agents are stateless between runs — you carry the conversation forward explicitly by passing the previous messages back in. This keeps the model honest about context and makes persistence trivial: the message log is just data you can serialise to a database.

A multi-turn conversation

agent = Agent('openai:gpt-5.2', instructions='Be a helpful assistant.')

# Turn 1
r1 = agent.run_sync('Who wrote Pride and Prejudice?')
print(r1.output)   #> Jane Austen

# Turn 2 — feed the prior messages back in
r2 = agent.run_sync(
    'When was she born?',
    message_history=r1.new_messages(),
)
print(r2.output)   #> Jane Austen was born on 16 December 1775.
  • result.all_messages() / result.new_messages() — the message log, as structured ModelMessage objects.
  • *_json() variants — serialise to JSON for storage, then reload to resume a conversation later.
  • History processors — register functions to summarise or trim history before each model call, controlling context-window cost on long chats.
11 Pydantic Graph

Pydantic Graph — For Complex Workflows

For most agents the built-in run loop is all you need. When control flow gets genuinely complex — multi-stage pipelines, explicit state machines, human approval gates — Pydantic AI offers pydantic-graph: a standalone, async graph library defined with type hints rather than decorators or DSLs. (Pydantic AI's own agent loop is built on it.)

Nodes as dataclasses; edges as return types

from __future__ import annotations
from dataclasses import dataclass
from pydantic_graph import BaseNode, End, Graph, GraphRunContext


@dataclass
class Ingest(BaseNode):
    async def run(self, ctx: GraphRunContext) -> Analyse:
        return Analyse()


@dataclass
class Analyse(BaseNode[None, None, str]):
    async def run(self, ctx: GraphRunContext) -> End[str]:
        return End('done')            # End[T] terminates the graph


graph = Graph(nodes=[Ingest, Analyse])
result = graph.run_sync(Ingest())
print(result.output)   #> done

The return type is the edge. A node's run() returns the next node (or End), so the graph's structure is statically known to your type-checker. No separate "add_edge" wiring to drift out of sync with the code. Graph state is a typed object threaded through every node via ctx.state, and runs are durable — they can be persisted and resumed.

12 Durable Execution & MCP

Durable Execution, MCP & Human-in-the-Loop

Production agents are long-running, fail mid-flight, and increasingly need to talk to external tool servers and pause for human approval. Pydantic AI ships first-class support for all three.

Durable execution

Wrap an agent so its runs survive process crashes, retries and multi-hour waits by delegating orchestration to a durable engine. Pydantic AI integrates with:

Temporal

Workflow engine — each model and tool call becomes a durable, replayable activity.

DBOS

Lightweight durable execution backed by Postgres, no separate server.

Prefect

Data-workflow orchestration with retries, observability and scheduling.

Restate

Durable, resilient handlers for long-running, stateful agent workflows.

Model Context Protocol (MCP)

Pydantic AI is both an MCP client — connect to any MCP server and expose its tools to your agent as a toolset — and supports being used inside MCP servers. This plugs agents into the wider tool ecosystem without bespoke integrations.

from pydantic_ai import Agent
from pydantic_ai.mcp import MCPServerStdio

server = MCPServerStdio('npx', args=['-y', '@modelcontextprotocol/server-filesystem', '.'])
agent = Agent('openai:gpt-5.2', toolsets=[server])   # remote tools, locally typed

Human-in-the-loop & AG-UI

Tools can require approval before they execute — the run pauses, surfaces the proposed call, and resumes once a human (or policy) signs off. Pydantic AI also implements AG-UI and A2A standards for streaming agent state to front-ends and coordinating between agents.

13 Observability & Evals

Observability, Evals & Testing

Because the framework comes from the Pydantic/Logfire team, the production story is unusually complete — debugging, evaluation and testing are all first-class rather than afterthoughts.

Logfire & OpenTelemetry

Add a few lines and every agent run is traced: the prompt, each model request/response, every tool call, token usage and validation retries — viewable as a waterfall. Logfire is built on OpenTelemetry, so traces also flow to any OTel backend (Jaeger, Grafana, Honeycomb…).

import logfire

logfire.configure()
logfire.instrument_pydantic_ai()    # every run now traced automatically

Pydantic Evals

pydantic-evals is a sister package for systematic evaluation: define datasets of cases, run your agent over them, and score with built-in or custom evaluators (exact match, LLM-as-judge, latency, assertions). Evals are the difference between "it worked in the demo" and "it works on the 200 cases that matter".

Testing with TestModel & FunctionModel

You should never hit a real LLM in a unit test. Pydantic AI provides drop-in fake models:

ToolUse it for
TestModelAuto-generates schema-valid outputs and exercises every tool — zero-config smoke tests.
FunctionModelYou write a function that plays the model — assert on exactly what the agent sends and control every reply.
Agent.override(model=...)Swap the model (and deps) inside a test without touching production code.
capture_run_messages()Inspect the full message exchange to assert on tool calls and retries.
 
from pydantic_ai.models.test import TestModel

def test_support_agent():
    with support_agent.override(model=TestModel()):
        result = support_agent.run_sync('My card was stolen!', deps=fake_deps)
    assert isinstance(result.output, SupportOutput)   # offline, deterministic
14 When to Choose It

When to Reach for Pydantic AI

✅ Great fit

  • You're a Python shop that already lives in Pydantic / FastAPI.
  • Structured, validated output is central (extraction, classification, form-filling).
  • You value type-safety, testability and clean DI over a giant feature surface.
  • You want production observability and evals without bolting on a separate stack.

🤔 Consider alternatives

  • You need a vast pre-built integration/tool catalogue today → LangChain ecosystem.
  • Your problem is fundamentally a hand-drawn state graph → LangGraph (though Pydantic Graph overlaps).
  • You want a "team of role-playing coworkers" metaphor → CrewAI.
  • You're not in Python.
